# peerdesk 工程规范（强制）

> **本文件是所有开发 agent 的强制前置读物。** 违反本规范的产出一律退回，不进入审查。
>
> 立规背景：M1a 首轮因"无规范、凭感觉写"被三方审查判出 11 Critical + 30+ Major 并整轮作废。
> 维护者结论：**"为了防止审查出来，写之前要规划和定好规范"** —— 审查是最后一道防线，不是第一道。
> 本规范的每一条都对应一个真实踩过的坑，不是教条。

## 0. 总则

1. **规范先行**：任何架构级改动（新增/重划模块边界、引入第三方库、改变进程内 ABI）**必须先出设计文档并过审，再写实现**。禁止"边猜边写"。
2. **这不是 demo**：按行业标准写生产代码。不接受"先跑通再说"的临时实现，除非在代码中以 `TODO(<里程碑>)` 明确标注并在 AGENTS.md 登记。
3. **诚实优先**：受阻就报卡点。**禁止把"编译通过"、"桩通过"说成"功能已验证"**（首轮真实事故：自报"Links clean"但磁盘零改动；lead 自己把 `STUB=ON` 的桩测试当成功能验证）。
4. **自述无效，实证有效**：完成标准是**贴出真实命令输出**，不是描述。

## 0.5 设计先行（强制，顺序不可颠倒）

**任何写代码的任务都必须先有设计文档并过审。** 设计文档按以下顺序组织，顺序即思考顺序：

### 第一步：业务逻辑（先写这个）
- **用户场景**：谁、在什么情况下、想达成什么。
- **业务流程**：正常流程逐步展开（谁在何时做什么、前置条件、后置状态）。
- **业务规则与约束**：权限、时效、配额、唯一性等规则，逐条可判定。
- **异常业务场景**：用户中途放弃、凭据过期、对端不在、重复操作、并发冲突……每条写明业务上应该如何表现。

### 第二步：技术流程（业务定稿后才写）
- **时序**：组件间调用与事件顺序（谁触发谁、何时、同步还是异步）。
- **状态机**：状态集合、合法迁移、非法迁移如何处理。
- **错误传播路径**：错误从产生点到用户可见提示的完整链路，每一跳的错误码/语义。
- **并发与线程模型**：哪些在哪个线程、锁的范围、回调归属。

### 第三步：模块划分（技术流程定稿后才写）
- **模块清单与职责**：一句话说清每个模块做什么、不做什么。
- **职责边界**：明确"这个不属于我"的部分归谁。
- **接口契约**：跨模块接口签名、允许过界的类型、所有权与生命周期。
- **依赖方向**：谁依赖谁，禁止循环依赖。

**禁止**：没有业务逻辑就写技术流程；没有模块划分就动手写代码。
**设计必须过审**（见 §8），未过审的设计不得进入实现阶段。

## 1. TDD（强制流程）

顺序不可颠倒：

1. **先写测试**，表达期望行为（含边界与失败路径）。
2. **确认测试失败**，且**失败原因正确**（不是编译错、不是路径写错）。
3. **写最小实现**让它通过。
4. **重跑全量验证**（见 §6）。

硬性要求：
- **禁止消音测试**。真实事故：`(void)connected;` 把"connected 永远不会发生"这个缺口消掉了。
  觉得某行为暂时无法验证时，写成**会失败的断言**或 `TODO` 标红，**不许静默绕过**。
- **测试必须验证行为，不能只验证"没崩"/"编译过"**。真实事故：桩不记录收到的 SDP，测试只断言"返回值非空"，而那是硬编码常量。
- **禁止只测自己写的 fake**。真实事故：客户端测试连的是测试文件里自己手写的 fake server，与真实服务端契约漂移不会变红。
  跨模块契约必须**对接真实实现**（Go 用 bufconn 起真 server，C++ 用进程内真实 gRPC，等等）。
- 并发代码**必须**跑竞态检测（Go: `go test -race`；C++: 有条件时 `-fsanitize=thread`）。

### 1.1 测试必须分两块写，缺任一块视为未完成

#### 第一块：业务流程测试（判据 = 设计文档的「业务逻辑」）
- **按设计里的业务流程逐条验证**，一个业务场景一个测试，测试名直接对应业务流程条目。
- 层级是**集成/端到端**：跨模块、对接真实依赖（Go 用 bufconn 起真 server + 真 DB；C++ 用进程内真实组件）。
  **禁止**用自己手写的 fake 顶替被集成方（真实事故：客户端测试连的是测试文件里自造的 fake server，契约漂移不会变红）。
- 必须覆盖设计里写明的**异常业务场景**（凭据过期、对端不在、重复操作、并发冲突、中途放弃……）。
- 这块回答的问题：**「业务跑得通吗、业务规则守住了吗」**。

#### 第二块：函数级技术测试（判据 = 设计文档的「技术流程 / 模块划分」）
- **按技术结构分模块组织**，目录/文件结构对应模块划分。
- **每个函数**都要有三类用例：
  1. **正常**：典型输入与预期输出。
  2. **异常**：非法入参、空指针/nil、依赖失败、错误码路径、异常抛出路径。
  3. **边界**：零/空/最大最小值、刚好到期与刚好未到期、容量满、重复调用、调用顺序颠倒、并发调用。
- 这块回答的问题：**「每个函数自己是对的吗」**。

> 两块缺一不可：只有业务测试 → 函数级缺陷（空指针、边界、并发）漏网；只有单元测试 → 组件各自正确但业务流程串不起来（真实事故：两端各自自洽，契约从未一起验证过）。

### 1.2 测试本身要过审（实现之前）
TDD 写完测试、**还没写实现**时先送审，此时返工成本最低。审查也**按上述两块分别审**：
- **业务流程测试** → **reviewer-2 主审**：测试表达的期望行为是否符合设计的业务逻辑与业务规则；设计里的异常业务场景有没有遗漏。
- **函数级技术测试** → **reviewer-1 主审**：是否按模块划分组织；**是否每个函数都有正常/异常/边界三类**；有无消音、有无只断言"不崩"、有无用硬编码常量假装验证。

两块都过审才能进入实现。

## 2. 分层与模块化

### 2.1 C ABI 层（`core-cpp/src/core.cpp`）—— 必须薄
只允许做四件事：**参数校验 / 句柄解引用 / 转发调用 / 异常拦截+错误码转换**。

- **单个导出函数 ≤ 约 15 行**。
- **禁止出现 `std::thread`** 或任何线程生命周期管理。
- **禁止调用任何 `Create*` 工厂**做对象装配。
- 禁止承载业务编排、握手流程、组件拆解顺序。

> 立规依据：首轮 `core.cpp` 391 行、`pd_session_start` **84 行**，在 ABI 层做对象装配+线程管理+握手编排+手工拆解顺序。
> `use-after-free SIGSEGV` 与 `joinable thread` 的 `std::terminate` **根源就是这个分层错误**——审查员逐条修"拆解顺序"，治的是症状。

### 2.2 内部实现层 —— 真 pimpl
装配、线程生命周期、编排、拆解顺序放内部 `Session` 类。
- **崩溃类缺陷靠 RAII 根治，不靠手工排顺序。** 析构顺序正确性应由成员声明顺序 + RAII 保证，而不是靠注释提醒下一个人别写错。
- 对外句柄保持 opaque（头文件只前向声明，无 struct 体）。

### 2.3 进程内 ABI 边界（硬约束）
跨**预编译第三方库**或**不同 C++ 标准库**的边界：
- **只允许 POD、`const char*` + 长度、整型错误码**过界。
- **禁止**传 `std::string` / STL 容器 / 含 STL 成员的类（含按值接收 `webrtc::RTCError` 这类）。
- **禁止**手写解读对方运行时的内存布局（如自制 `DecodeForeignStdString`）。遇到 ABI 不匹配，**消除 ABI 混用**，不写兼容层。

> 立规依据：实测 `STUB=OFF` **链接成功但运行时数据损坏**（libc++ `sizeof(std::string)=24` vs libstdc++ `=32`，虚函数走 vtable + 无参工厂 mangled name 相同 → 链接器发现不了）。兼容层是治标且会掩盖问题。

## 3. 错误处理

1. **C ABI 边界必须捕获所有异常**（异常逃逸到 Dart FFI 是 UB），**但捕获 ≠ 吞掉**：
   - 有回调通道（如 `on_error`）就**必须上报诊断信息**。
   - 无回调通道（如 create 失败）则在注释中写明"此处无回调通道，信息只能经返回值传达"。
2. **错误码语义必须准确**：不许用一个笼统码覆盖不同原因。
   真实事故：`catch(...) → PD_ERR_TRANSPORT` 把 `bad_alloc` 谎报成"传输错误"，误导排查方向。
3. **服务端错误码必须端到端保真**：`Unauthenticated` / `PermissionDenied` / `ResourceExhausted` / `InvalidArgument` 不得在任何一层被压平成 `Internal` 或 `TRANSPORT`，否则上层无法给用户正确提示。
4. **禁止沉默失败**：静默丢弃、吞异常、失败返回默认值一律禁止。至少要有一条可定位日志。
   真实事故：`OnRemoteIce` 收到候选一声不吭丢弃；`trySend` 缓冲满即静默丢包。

## 4. 并发

- 回调的线程归属必须在头文件/接口注释中写明（谁的线程、能否重入、能否在回调里调哪些方法）。
- **禁止持锁调用用户回调**（锁跨越任意用户代码 → 锁序倒置）。做法：锁内拷出指针/数据，出锁再调。
- 可能在回调线程上被调用的方法，必须处理"自己 join 自己"（真实事故：回调里调 `Disconnect()` → 读线程自 join → `Resource deadlock avoided` 崩进程）。
- 公开入口必须防重入（真实事故：`pd_session_start` 调两次 → use-after-free）。

## 5. 安全（服务端）

- **鉴权在 interceptor 统一做，不在业务函数里零散判定。**
  > 维护者点名的反模式：*把"注册"的判定塞进 JWT 鉴权拦截器* —— 注册的人还没有账号。
  > 反过来也禁止：**业务方法里手写鉴权**。职责要分清：interceptor 管"你是谁"，业务函数管"你能做什么"。
- **永不信任客户端自报身份**。`user_id` 一律从已验证 token 取，请求里的同名字段标 `deprecated` 并忽略。
- 凭据只存哈希（Argon2id 等），token 分型（`typ=access/refresh`，互不可代用）。
- 任何校验型接口必须防爆破（失败计数 + 锁定/限流）。
- DB 外键声明了就必须启用（SQLite 需显式 `PRAGMA foreign_keys=ON`）。
- 不靠错误文案判断 DB 错误类型（用 driver 的错误码，换库才不失效）。

## 6.5 日志（当前最薄弱环节，强制整改）

**实测现状（立规依据）**：Go 仅 `log.Printf`×11 / `log.Fatalf`×9，**无任何级别概念**；core-cpp 用 `fprintf`/`printf` 直打 stderr。
后果：连接失败时**无法追溯是信令、鉴权、入房、SDP、ICE、DTLS 还是 DataChannel 哪一环断的**；异常被 catch 后不留痕。
对远程控制软件，日志就是唯一的现场，这是不可接受的。

### 6.5.1 统一日志模块（三端各自实现，语义一致）
- **必须分级**：`DEBUG` / `INFO` / `WARN` / `ERROR`。级别可运行时配置，`DEBUG` 默认关但可开。
- **必须结构化**：带上下文字段，至少包括 `session_id` / `device_id` / `peer_id` / `role` / 模块名。禁止把上下文拼进自由文本。
- **禁止**在业务代码里直接用 `printf` / `fprintf` / `std::cout` / `log.Printf` 裸调用；统一走日志模块。
- `Fatal` 只允许出现在进程启动失败路径（如端口占用），**业务路径禁止 Fatal**。

### 6.5.2 关键状态迁移必须有日志（缺一条即不合格）
连接链路每一跳都要可追溯：
| 环节 | 级别 | 必须记录 |
|------|------|---------|
| 信令连接建立/断开 | INFO | 地址、结果、耗时 |
| 鉴权（JWT 校验） | INFO/WARN | 成功(user)/失败(原因码)，**不记 token 本身** |
| 配对码校验 | INFO/WARN | 成功/失败/锁定，**不记码本身** |
| 入房 / 离房 | INFO | room、peer、role、当前房内人数 |
| SDP offer/answer 收发 | DEBUG | 类型、长度、摘要（不必全文） |
| ICE 候选收发 / ICE 状态迁移 | DEBUG | 候选类型(host/srflx/relay)、状态变化 |
| DTLS / 连接状态迁移 | INFO | 旧态→新态 |
| DataChannel open/close | INFO | 通道名、id、配置(ordered/maxRetransmits) |
| 会话建立成功 / 失败终止 | INFO/ERROR | 总耗时、失败原因链 |
| 周期性质量指标 | DEBUG | RTT、丢包、码率、帧率（后续接入） |

### 6.5.3 异常绝不允许被吃
- 每个 `catch` / `if err != nil` 分支**必须**留日志（含原因与可定位上下文），或明确向上传递。
- **禁止空 catch、禁止只 `return false` 不留痕**。
- 静默丢弃数据（如缓冲满丢包）**必须** WARN 级记录并计数。

### 6.5.4 脱敏（硬要求）
`access_token` / `refresh_token` / 配对码 / 密码 / 密钥**一律不得进日志**（含 DEBUG 级）。
必要时只记长度或前若干位掩码。

## 7. 环境须知

- 本机有 `http_proxy` 但无 `no_proxy` → 任何 localhost 操作前必须
  `export no_proxy="127.0.0.1,localhost,::1"; export NO_PROXY="$no_proxy"`，否则本地连接被代理劫持返回 502。
- 无 GPU、无 Windows：GPU/硬编与 Windows 专有路径只能靠 CI 与维护者本机验证，**不得声称已验证**。

## 8. 审查（对照设计，不凭感觉）

审查发生在两个阶段，**都必须以设计文档为判据**，不是凭个人口味。

### 8.1 设计评审（写代码之前）
- **reviewer-3（结构/常识）主审**：业务逻辑是否自洽、技术流程是否合理、模块划分是否干净、有无职责错位/因果倒置/概念混淆。
- **reviewer-2（业务）**：业务规则是否完整、异常业务场景是否遗漏。
- 设计未过审，**不得进入实现**。
> 立规依据：审查员擅长在给定结构里找 bug，**不擅长质疑结构本身**。M1a 首轮的结构性问题（ABI 层过厚）三个审查员都没提，被维护者一眼看出——所以结构问题必须在设计阶段解决。

### 8.2 测试评审（TDD 写完测试、实现之前）——**按两块分别审**
| 测试块 | 主审 | 判据 | 审什么 |
|--------|------|------|--------|
| **业务流程测试** | reviewer-2 | 设计的**业务逻辑** | 是否逐条覆盖业务流程；异常业务场景有无遗漏；是否用真实依赖而非自造 fake |
| **函数级技术测试** | reviewer-1 | 设计的**技术流程/模块划分** | 是否按模块组织；**每个函数是否都有正常/异常/边界**；有无消音、有无只断言"不崩"、有无用硬编码常量假装验证 |

两块都过审才进入实现。任一块不合格，退回补测试，**不得先写实现**。

### 8.3 实现评审（实现完成后）
| 审查员 | 判据 | 看什么 |
|--------|------|--------|
| **reviewer-1 代码** | 设计的**模块划分**与本规范 | 代码是否规范、是否模块化、有无乱揉/逻辑混乱、模块边界有没有被破坏、并发与资源生命周期、错误处理与日志是否合规 |
| **reviewer-2 业务** | 设计的**业务逻辑**与**业务流程** | 实现是否真的按业务流程走、业务规则有没有被绕过或遗漏 |
| **reviewer-3 结构/常识** | 设计整体 | 实现是否偏离设计、有没有为绕开困难而悄悄改变架构、是否符合常人思维 |

**三位都必须回答一个共同问题：这份实现和设计文档对得上吗？** 对不上就是不合格，哪怕代码本身"能跑"。
